# Deploy

Kubernetes manifests and Helm charts for deploying Kuvera to a cluster.

## Layout

```
deploy/
├── helm/           # Helm chart(s) for production and staging deploys
└── manifests/      # Raw Kubernetes manifests (dev cluster, CI)
```

## Quick start (dev cluster)

```bash
make dev-cluster       # boots a kind cluster with eBPF support (idempotent)
make deploy-dev        # stub until T5.4: prints "not yet implemented"
make dev-cluster-down  # tears the kind cluster down
```

`make dev-cluster` is idempotent: re-running it against an existing cluster
just re-checks node readiness. Pass `KIND_RECREATE=1` to delete and rebuild
(e.g. after editing `deploy/dev/kind-config.yaml`). Common overrides:

```bash
make dev-cluster KIND_CLUSTER_NAME=kuvera-test   # alternate cluster name
make dev-cluster KIND_NODE_IMAGE=kindest/node:v1.36.1   # pin the node image
make dev-cluster KIND_RECREATE=1                 # force a clean rebuild
```

Docker is the only supported runtime. See
[docs/DEVELOPMENT-SETUP.md](../docs/DEVELOPMENT-SETUP.md) for install steps.

After the cluster is up, verify the eBPF prerequisites:

```bash
scripts/dev-cluster-verify.sh   # nodes Ready + BTF present on a node
```

[docs/TESTING.md](../docs/TESTING.md) covers the offline config test and the full
live cluster check, including loading an eBPF program.

## Helm chart

The `helm/kuvera/` chart installs all Kuvera components into a single
namespace. Values files for different environments live alongside the chart.

## Manifests

`manifests/` contains raw YAML for ad-hoc dev and CI use: the sensor
DaemonSet, RBAC resources, and CRD definitions. These are also generated by
the Helm chart, but raw manifests are useful for `kubectl apply` during
development.

## eBPF requirements

The dev cluster (kind) must have:
- BTF available at `/sys/kernel/btf/vmlinux`
- `/sys/fs/bpf` mounted into nodes
- `/sys/kernel/debug` accessible

`make dev-cluster` configures this automatically via `deploy/dev/kind-config.yaml`.
