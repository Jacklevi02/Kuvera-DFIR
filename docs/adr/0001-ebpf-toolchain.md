# ADR 0001: eBPF toolchain

- **Status:** Accepted
- **Date:** 2026-11-02
- **Ticket:** T2.1 (#14), parent EPIC-2

## Question

Which combination of clang version, libbpf headers, kernel BTF requirements, and
`cilium/ebpf` version produces a reliably-loading CO-RE program on the kind node
kernel?

## Decision

| Piece       | Choice                                    | Pinned in             |
| ----------- | ----------------------------------------- | --------------------- |
| clang       | 23.1 (`conda:clang-23`, compiler only)    | `mise.toml`           |
| bpftool     | 7.8                                       | `mise.toml`           |
| libbpf      | 1.8.0 headers, checksum-verified on fetch | `sensor/bpf/Makefile` |
| cilium/ebpf | v0.22.0                                   | `sensor/go.mod`       |
| `golang.org/x/sys` | v0.49.0, above cilium/ebpf's v0.43.0 | `sensor/go.mod`     |
| `vmlinux.h` | Committed snapshot, regenerated by hand   | `sensor/bpf/vmlinux.h` |
| Instruction set | `-mcpu=v3`                            | `sensor/bpf/Makefile` |
| Kernel      | BTF at `/sys/kernel/btf/vmlinux` and cgroup v2 | Not pinnable     |

The versions above record what was tested on the date of this ADR. The files in
the last column are the live pins, per [TOOLCHAIN.md](../TOOLCHAIN.md).

The ticket names `sensor/bpf/Makefile` as the home for all non-Go pins. clang and
bpftool are in `mise.toml` instead, because CLAUDE.md and TOOLCHAIN.md require
every CLI to live there. The Makefile reads the clang pin from `mise.toml` and
refuses to build with any other version, so it still enforces the pin without
holding a second copy.

### Build recipe

The full version is `sensor/bpf/Makefile`. The part that matters:

```make
LIBBPF_VERSION := 1.8.0
BPF_CPU := v3
CLANG ?= clang-23

BPF_CFLAGS := -target bpf -mcpu=$(BPF_CPU) -O2 -g \
	-D__TARGET_ARCH_x86 \
	-Wall -Werror \
	-fms-extensions -Wno-microsoft-anon-tag \
	-ffile-prefix-map=$(CURDIR)=. \
	-I. -I$(LIBBPF_DIR)

build/%.bpf.o: %.bpf.c $(HEADERS) $(LIBBPF_HEADERS) | check-clang
	$(CLANG) $(BPF_CFLAGS) -c $< -o $@
```

| Flag                | Why                                                                                                       |
| ------------------- | --------------------------------------------------------------------------------------------------------- |
| `-g`                | BTF and CO-RE relocations are produced from debug info. Removing it removes CO-RE.                        |
| `-mcpu=v3`          | Fixed so a clang upgrade cannot silently raise the kernel floor.                                          |
| `-fms-extensions`   | Linux 7.2 BTF has anonymous tagged members, such as `struct slock_owned;` in `socket_lock_t`. Without this flag clang warns and drops those members, so `-Werror` fails the build. |
| `-ffile-prefix-map` | Keeps the checkout path out of the object.                                                                |

## Evidence

Tested on 2026-11-02 on Linux 7.2.13 (Fedora 44, x86-64), Docker 29.9.2 in normal
mode, kind 0.32, `kindest/node:v1.36.1`, containerd 2.3.1, cgroup v2.

The test program had the same shape as T2.2: a `sched_process_exec` tracepoint,
`BPF_CORE_READ`, and a BPF ring buffer. A Go loader ran as root inside a kind
worker node. It attached the program, ran a shell that ran a probe binary, and
required the probe's event to arrive with correct fields. Two checks cannot pass
by accident:

- `task->tgid`, read through CO-RE, had to equal the value from
  `bpf_get_current_pid_tgid()`.
- A variant used hand-written structs with deliberately wrong layouts, placing
  `tgid` at offset 0. The verifier log shows the load relocating it to offset
  2876, and the value came back correct.

**Compile and load matrix**, across clang 21.1.8, 22.1.8 and 23.1.4:

| libbpf \ cilium/ebpf | v0.20.0, v0.21.0 | v0.22.0                                   |
| -------------------- | ---------------- | ----------------------------------------- |
| 1.6.3                | Fail to load     | Compile fails with the full `vmlinux.h`   |
| 1.7.0                | Fail to load     | Pass                                      |
| 1.8.0                | Fail to load     | Pass                                      |

Two hard floors come out of this:

- **cilium/ebpf v0.22.0.** Earlier releases fail with `parsing .BTF header: header
  contains non-zero trailer`, because Linux 7.1 extended the BTF header. The
  v0.22.0 release notes confirm that older versions do not work on 7.1 and later.
- **libbpf 1.7.0.** The 1.6.3 headers fail with `conflicting types for
  'bpf_stream_vprintk'`, because their declaration collides with the kernel's in
  `vmlinux.h`. The same headers pass with hand-written types, so the failure
  comes from the header's age relative to the kernel.

clang made no difference across the three versions. 23.1 is the newest of them.
The matrix ran with `-isystem` around `vmlinux.h`. The final flags
(`-fms-extensions`) were tested with the pinned versions only.

**Further checks on the pinned combination:**

| Check                                                   | Result                                     |
| ------------------------------------------------------- | ------------------------------------------ |
| 50 consecutive runs on a worker                         | 50 of 50 pass                              |
| Control-plane node                                      | Pass                                       |
| Output of the real `sensor/bpf/Makefile`                | Loads and captures                         |
| `bpftool prog load` inside a node (T2.2's criterion)    | Pass, using a static bpftool copied in     |
| Clean `ubuntu:24.04` container: `mise install` and build | Pass, 7 s install, 578 MB on disk         |
| Negative: a field no kernel has                         | Refused, instruction poisoned by CO-RE     |
| Negative: unprivileged user                             | Refused, `operation not permitted`         |
| Negative: `license` set to `Apache-2.0`                 | Refused by the verifier, see [Open items](#open-items) |
| Negative: wrong clang, tampered libbpf archive          | Build stops                                |

### What this does not show

- **Only one kernel was tested.** A kind node has no kernel of its own, so "the
  kind node kernel" means the host's. CI's `ubuntu-24.04` runner has a different
  kernel, and it has not run any of this. T2.5 is the first check that will.
- **Older kernels are untested.** Upstream documents BPF ring buffers from Linux
  5.8, so that is the expected floor, not a verified one. BL-IN-1 is where it
  gets verified.
- **x86-64 only.** `vmlinux.h` and `__TARGET_ARCH_x86` are per-architecture.
- **Loads ran as root.** The minimal capability set belongs to T5.2.
- **The load tests used an older `x/sys`.** cilium/ebpf v0.22.0 requires
  `golang.org/x/sys` v0.43.0, and every test above ran on that version.
  `sensor/go.mod` raises it to v0.49.0 to clear
  [GO-2026-5024](https://pkg.go.dev/vuln/GO-2026-5024) (CVE-2026-39824). That bug
  is in `NewNTUnicodeString` in the `windows` package, which the Linux sensor does
  not build. Nothing imports cilium/ebpf yet, so T2.3 is the first code to
  exercise v0.49.0.
- **Reproducibility is partial.** Two builds in one environment are
  byte-identical, also from different checkout paths. A build on Fedora and one
  on Ubuntu, with the same compiler and inputs, have the same size but differ in
  194 bytes of BTF string ordering. The cause was not investigated.

## Kind-specific notes

These all caught the spike out, and T2.2 to T2.5 will meet them too.

- **PIDs differ.** BPF reports initial-namespace PIDs, and a process in a node
  sees the node's PID namespace. `cmd.Process.Pid` will not match an event's
  `tgid`. Match on file name, or compare against the helper.
- **`/tmp` is `noexec` in a node.** A test that drops a binary there and runs it
  through `sh` fails quietly, with no event.
- **Tracepoints are host-wide.** A program in a node sees exec events from the
  host and from every other node. Tests must filter, and on a busy machine must
  expect unrelated events.
- **Cgroup IDs.** `bpf_get_current_cgroup_id()` matched the inode of the node's
  own cgroup directory, `/sys/fs/cgroup/init.scope`. Nodes use a private cgroup
  namespace. Resolving a pod's cgroup was not verified here and belongs to T2.4.
- **Tracing is available.** Attaching worked with no change to
  `deploy/dev/kind-config.yaml`.
- **Nodes have no bpftool.** Copy the static binary in with `docker cp`.

## Alternatives considered

**Generate `vmlinux.h` at build time.** This is what the old `.gitignore` entry
assumed. Rejected because the build would depend on the kernel of whichever
machine runs it, and both build failures above came from a new kernel's
`vmlinux.h`. A host kernel update would be able to break the build with no change
in the repo. The cost of the snapshot is 3.6 MB in git, plus a one-off regeneration
when a program needs new types. CO-RE means it does not need to match the target
kernel.

**Hand-written minimal types.** The wrong-layout variant proves this works, and it
produces 9 KB objects instead of 935 KB. Rejected for now because every new field
needs a hand-written declaration, and a typo only surfaces as a load failure
instead of a compile error. It is worth revisiting if object size starts to matter.

**`bpf2go`.** It generates Go bindings and is the usual `cilium/ebpf` route.
Rejected because the tickets already plan `.bpf.o` files, `go:embed` in T4.2, and a
Makefile, and because it would add committed generated objects. This can be
revisited at T4.2 without changing any pin here.

**`conda:clang`.** Rejected because it also installs GNU `ld`, `as`, `strip` and
`objcopy`, which would shadow system binutils for everyone in the repo, and it
takes 1.2 GB. `conda:clang-23` is the compiler alone.

**A pinned Docker builder image.** Rejected because it would be the only tool
outside `mise.toml`, and `make` would need the Docker socket.

**Vendoring libbpf headers.** Rejected as more committed third-party code with no
gain over a checksum-verified fetch.

## Consequences

- `mise install` adds about 580 MB to every machine and CI job. mise-action caches
  it, but the first run of each cache key pays for the download.
- Activating mise puts `conda:clang-23`'s `bin/` on `PATH`. That is `clang-23` plus
  incidental utilities such as `zstd` and `xmllint`.
- Building programs needs network access on the first run, to fetch libbpf.
- There is no `llvm-strip`, so objects keep their DWARF, at about 935 KB each.
  That is fine against T5.1's 50 MB limit. `conda:llvm-tools` would add it.
- `cilium/ebpf` has no global BTF cache as of v0.22.0, so T4.2 should share a
  `btf.Cache` across its four programs.
- A kernel that changes the BTF format can break the loader, as Linux 7.1 did. When
  a developer's kernel moves, a `cilium/ebpf` bump may be needed first.

## Follow-ups

- **T2.2:** add `make -C sensor/bpf` to the root `build`, `test` and `lint` targets
  when the first program lands. `*.bpf.o` is gitignored, so `go:embed` needs the
  objects built first. The ticket says "perf ring buffer"; the tested map type is
  `BPF_MAP_TYPE_RINGBUF`.
- **T2.3:** delete `sensor/tools.go` once real code imports `cilium/ebpf`.
- **T2.5:** run in CI's `Live cluster` job, which adds the second kernel.
- **T5.1:** the Dockerfile's build stage needs the same clang and bpftool pins.

## Open items

**The `license` string needs a decision before T2.2.** `bpf_probe_read_kernel`, and
so `BPF_CORE_READ`, is GPL-only. The verifier refuses a program declaring
`Apache-2.0`, so `sensor/bpf/*.bpf.c` cannot simply follow the repo's licence.
`GPL` and `Dual BSD/GPL` both load. The recommendation is `Dual BSD/GPL` with a
matching SPDX header.

The committed `vmlinux.h` is generated from kernel type information. Neither this
nor the BPF licensing has had legal review, and this ADR makes no claim about
either. Both should go through a licence check before the sensor is released.
